Interview study guide

    SeatRush

    A flash-sale ticket booking system. Nginx is the gateway doing every job a gateway should do; Postgres guarantees that two people can never own the same seat. This page is everything I need to defend it.

    1

    Pitches

    ▾

    The 30-second pitch

    SeatRush is a concert ticket site built around a flash sale — booking opens at an exact second and hundreds of people rush the same seats. Two hard problems: the traffic spike, and never selling one seat twice. I put Nginx in front as a real gateway — load balancer, rate limiter, microcache, TLS — and I put the correctness guarantee in Postgres, in a single conditional UPDATE that makes the check and the write the same statement. To prove it I ran three hundred users at ten seats with the rate limiter switched off: ten seats, ten bookings, zero oversold, and the two hundred and ninety-one who lost got a clean 409 telling them which seat went.

    The 2-minute walkthrough

    The problem is a flash sale. Booking opens at an exact instant, so you get a traffic spike and a contention spike at the same moment — everybody wants the same few good seats.

    The shape is a React single-page app, Nginx, three identical FastAPI replicas, and one Postgres. The replicas are completely stateless — auth is a JWT, every piece of mutable state is in the database — and that one property is what lets Nginx round-robin them with no sticky sessions and survive one dying.

    Nginx is doing six jobs. It terminates TLS, serves the React build, balances the three replicas and fails over when one dies, rate-limits three different ways, and microcaches the seat map for one second. That last one is the interesting one: every open tab polls the seat map every two and a half seconds, so a thousand viewers is four hundred requests a second asking the identical question. A one-second cache with cache_lock collapses that to about one backend request per second — and I measured that it stays flat whether forty or two hundred people are watching.

    Correctness is one SQL statement. Claiming seats is a conditional UPDATE whose WHERE clause is the eligibility rule, so the check and the write cannot come apart. Two transactions on the same row: the second blocks, and when the first commits Postgres re-evaluates its WHERE clause against the new row version and it matches nothing. On top of that there is a unique constraint on seat_id in the bookings join table, so the database refuses to oversell even if my code is wrong.

    And it is all verified, not asserted: fifty-eight tests, a seventy-one-check verification script, and a load test with three separate modes.

    The 5-minute deep dive — outline

    1. The problem (30s) — flash sale = traffic spike + contention spike at the same instant. Two independent failure modes: the backend melting, and overselling.
    2. The shape (45s) — SPA → Nginx → 3 stateless FastAPI → 1 Postgres. Why stateless is the load-bearing property.
    3. Reads: the microcache (60s) — the poll storm arithmetic, the 1-second window, proxy_cache_lock as the thundering-herd fix, and why staleness is safe here specifically.
    4. Writes: the claim (90s) — the conditional UPDATE, the two-transaction timeline, EvalPlanQual recheck, all-or-nothing rollback, and UNIQUE(seat_id) as defence in depth.
    5. Retries and duplicates (45s) — Nginx never retries POSTs; idempotency keys absorb what it cannot prevent; why they share one transaction.
    6. Proof (60s) — direct-mode load test numbers, the failover log line showing "504, 200", the per-token rate limit measurement.
    7. What I'd change (30s) — the honest list: secrets, managed Postgres with a read replica, shared rate limits across nodes, WebSocket + Redis for live updates, and what breaks first at 100×.

    The problem and the requirements

    ▾

    A flash sale is unusual because it creates two spikes at the same instant, and they need different solutions.

    Spike 1 — traffic

    Thousands of people load the seat map and watch it. Reads dominate, they are nearly all identical, and they repeat every few seconds.

    Solved at the edge — caching and rate limiting. Never in the app.

    Spike 2 — contention

    Everyone wants the same few good seats in the same millisecond. Writes are few but they all collide on the same rows.

    Solved in the database — row locks and transactions. Never at the edge.

    Confusing the two is the classic mistake: a cache cannot make writes safe, and row locks cannot absorb a read storm.

    Functional requirements

    • Browse events; see live seats-remaining and whether the sale is open.
    • Pick up to 6 seats and hold them for 5 minutes.
    • Pay (simulated) to convert a hold into a booking with a code.
    • See my tickets.
    • Admin: create an event with a generated seat map, see live stats with an integrity check, reset an event for a demo.

    Non-functional requirements — the ones that shaped the design

    RequirementHow it is metHow it is proved
    Never oversell a seat Conditional UPDATE under row locks + UNIQUE(seat_id) 300 users / 10 seats direct at the DB → 0 oversold; 50 users / 1 seat → exactly 1 winner
    Never double-book on a retry Idempotency keys in the same transaction; Nginx never retries POSTs 10 concurrent duplicates of one key → 1 hold, 10 identical 201s
    Survive a replica crash 3 stateless replicas, passive health checks, proxy_next_upstream kill api2 → 12/12 requests still 200, two showing a retry
    Handle a refresh storm 1-second microcache + proxy_cache_lock Backend load flat at ~1–2 req/s whether 40 or 200 viewers poll
    Resist spam and brute force Three leaky-bucket zones: per-IP, per-IP login (r/minute), per-token 120 req → 45×429; 8 logins → 4×429; token A throttled while token B on the same IP was not
    Holds must not leak Lazy expiry, re-checked on every read and inside the claim Expired hold frees its seat with no sweeper running; confirming it → 410
    No wrong-clock bugs Sale gate uses Postgres now(); UI counts down to /api/time Booking before sale_opens_at → 403 regardless of client clock

    Deliberate non-goals

    No Redis, no WebSockets, no background workers, no message queue, no ORM, no Kubernetes. Each of those is argued in Decisions; the short version is that none of them was needed, and every one would have added a second place where seat state could live.

    Architecture

    ▾
    The whole system. Six containers; only Nginx is reachable from outside.

    Why each component exists

    ComponentIts jobWithout it
    Nginx TLS, static files, load balancing, failover, rate limiting, microcache, structured logs Every replica needs its own cert and public port; a poll storm hits Postgres; brute-forcing login is free
    api1 / api2 / api3 Business rules and the SQL that enforces them One replica = one point of failure, and nothing to load balance
    PostgreSQL The only place seat ownership is decided Nothing else in the stack can make “exactly one owner per seat” true
    migrate (one-shot) Applies the schema and seeds, then exits; replicas wait for it The first replica to boot races the migration and crashes on a missing table

    Why “stateless replicas” is the load-bearing idea

    Each replica holds no mutable state: no session store, no in-process cache, nothing sticky. Auth is a self-contained JWT verified with a shared secret; seats, holds, bookings and idempotency keys all live in Postgres.

    Three consequences follow from that single property, and they are the backbone of the design:

    1. Any replica can serve any request, so plain round robin is correct. No ip_hash, no session affinity.
    2. A replica can die mid-session with no user-visible loss, so passive failover plus a retry is enough.
    3. Scaling out is one line in the upstream block, not a re-architecture.

    The cost: every authenticated request carries a ~160-byte JWT, and a revoked user stays valid until exp. Both acceptable here; the fix for the second is a deny-list.

    If an interviewer asks “why three replicas and not one?” — one replica would make the load-balancing and failover stories untestable. Three is the smallest number where round robin is visibly a rotation rather than an alternation, and where you can kill one and still have redundancy.

    Why each constraint exists

    booking_seats UNIQUE (seat_id) — the one that matters most

    backend/app/schema.sql:70–84
    CREATE TABLE IF NOT EXISTS booking_seats (
    booking_id uuid   NOT NULL REFERENCES bookings(id) ON DELETE CASCADE,
    seat_id    bigint NOT NULL REFERENCES seats(id) ON DELETE CASCADE,
    PRIMARY KEY (booking_id, seat_id),
    -- ***THE LAST LINE OF DEFENCE AGAINST OVERSELLING.***
    -- The application logic is what makes double-booking impossible in
    -- practice. This single-column UNIQUE is what makes it impossible
    -- *even if that logic has a bug*.
    UNIQUE (seat_id)
);

    Note it is a single-column unique, not part of the composite primary key. The PK (booking_id, seat_id) only stops the same seat appearing twice in the same booking. UNIQUE(seat_id) stops it appearing in any other booking, ever. That distinction is the whole point, and it is a good thing to be asked about.

    idempotency_keys PRIMARY KEY (user_id, key)

    This is not bookkeeping, it is the concurrency primitive. Two simultaneous inserts of the same key cannot both succeed, so exactly one caller does the work — and the loser blocks on the key, then reads the committed response. Scoped per user so two users may legitimately pick the same UUID (test_key_is_scoped_per_user).

    The smaller ones

    • bookings.hold_id UNIQUE — one booking per hold, so a duplicate confirm that somehow slipped past the idempotency layer still cannot create a second booking.
    • bookings.booking_code UNIQUE — codes get read aloud and typed; collisions must be impossible, not improbable. The insert retries behind a SAVEPOINT on collision.
    • seats UNIQUE (event_id, label) — no two “C7”s in one venue.
    • CHECK (status IN (…)) on every status column — the state machines are enforced by the schema, not by convention.
    • events CHECK (rows BETWEEN 1 AND 10) — bounds the seat map so one admin typo cannot generate a million rows.

    Money is integer cents everywhere. Floats cannot represent money.

    Concurrency deep dive

    ▾

    This is the part the whole project exists to prove.

    backend/app/holds.py:59–70 — CLAIM_SEATS_SQL
    UPDATE seats
   SET status = 'held', hold_id = $1
 WHERE event_id = $2
   AND id = ANY($3::bigint[])
   AND (status = 'available'
        OR (status = 'held' AND hold_id IN (
              SELECT id FROM holds
               WHERE status = 'active' AND expires_at < now())))
RETURNING id

    Three things are packed into one statement, and that is the design:

    1. The eligibility rule — a seat is claimable if it is available or its hold has aged out.
    2. The write — take it.
    3. The receipt — RETURNING id tells us exactly which ones we actually got.

    Then one line of Python decides everything: if len(got) != len(seat_ids): raise.

    Two transactions racing for seat 5

    The re-evaluation at t5 is the crux. T2 does not act on what it read at t2.

    Say this sentence and stop: “The check and the write are the same statement, so there is no window between them.” A SELECT then UPDATE has that window — that is the lost update.

    All-or-nothing

    If Bob had asked for seats 4, 5 and 6, the rollback at t7 also releases 4 and 6, which he had briefly won. A half-claim never becomes visible — he does not end up with two seats out of three and a hold he did not want. Verified by test_all_or_nothing_partial_claim_rolls_back.

    Deadlocks

    Two transactions can lock the same seats in opposite orders. Postgres detects the cycle and aborts one with 40P01, which from the client's point of view is indistinguishable from losing the race — so claim_seats catches asyncpg.DeadlockDetectedError and returns the same 409 rather than a 500.

    Everything above is the application being careful. The database is careful independently:

    Idempotency

    ▾

    The problem

    A user taps “Pay”, the response is lost to a flaky network, the client retries. Or they double-click. Or a mobile browser replays the request on reconnect. Retries are unavoidable in a distributed system, so the server must be able to recognise one.

    The contract

    SituationResult
    Same key, same bodyThe original response, replayed. Work done once.
    Same key, different body422 idempotency_mismatch — a key is a receipt for one specific request
    Same key, different endpoint422 — keys do not cross endpoints
    No key on a POST that creates something400 idempotency_key_required — refused at the door
    Two users pick the same UUIDBoth fine — the PK is (user_id, key)
    The original request failedThe key row rolled back with it, so the same key may be retried

    The client mints one key per user action — not per HTTP attempt — and reuses it on every retry of that action:

    frontend/src/state.jsx:230–250 — useAction
    const run = useCallback(async (...args) => {
  if (busy) return undefined;              // double-click guard
  if (!keyRef.current) keyRef.current = newIdempotencyKey();
  setBusy(true);
  try {
    const result = await fn(keyRef.current, ...args);
    keyRef.current = null;   // success → next click is a NEW action
    return result;
  } finally { setBusy(false); }
}, [busy, fn]);

    The flow

  POST + key ──────▶│  BEGIN                           │
                    │                                  │
                    │  INSERT idempotency_keys         │
                    │  ON CONFLICT (user_id,key)       │

                    └───────────┬──────────────────────┘
                                │
              ┌─────────────────┴──────────────────┐
         got a row                            no row

              │                                   │

     ② do the real work                SELECT the stored row
     ③ store status + body             ├─ different hash? → 422
              │                        ├─ no body yet?    → 409 (unreachable)
              ▼                        └─ replay status + body, DO NO WORK
           COMMIT                                 │
              │                                   ▼
              └──────────────▶ response ◀─────────┘

    Why it is safe under concurrent duplicates — the subtle part

    Two replicas get the same key at the same instant — a double-click that Nginx round-robins to api1 and api2. Both run the same INSERT … ON CONFLICT DO NOTHING.

    ON CONFLICT DO NOTHING does not return early on an in-flight conflicting row. It blocks. Postgres takes a speculative-insertion lock and waits for the other transaction to finish. This is the single detail that makes the whole scheme work, and it is the thing most people get wrong when they describe it.

    Then one of two things is true:

    • the other transaction committed → we get no row back, and because READ COMMITTED takes a fresh snapshot per statement, our very next SELECT can see the committed row, response body included. We replay it.
    • the other transaction rolled back (it hit 409 seat_taken, say) → no row exists, our insert succeeds, and we legitimately do the work.

    So the work happens exactly once, and the loser waits rather than racing. Verified by test_concurrent_duplicates_of_one_key: ten simultaneous copies of one request → one hold, one key row, ten identical 201s.

    Why it shares the business transaction

    If the key were recorded in its own transaction there would be a window where the key says “done” but the booking has not committed — or the booking committed and the key did not. Putting both in one transaction makes “work done” and “key recorded” a single atomic fact. Either both are visible or neither is.

    Why a failed request frees its key

    Because a rejected request must leave no trace. If losing a seat race burned the key permanently, the user's retry would replay a 409 forever even after the seat came free. test_a_failed_request_frees_its_key_for_retry checks exactly that: the loser's key row is gone, the winner's survives, and the loser can reuse their key successfully once the seat is released.

    How this complements Nginx

    Nginx is configured to never retry POSTs, so the edge never manufactures a duplicate on its own. This layer handles the duplicates the edge cannot prevent: the user's own double-click and the browser's own retry. Two different problems, two different layers.

    The jsonb detail worth volunteering. response_body is jsonb, which stores a parsed binary form — so Postgres does not preserve key order. The replayed response is semantically identical but not byte-identical, which is why the test asserts deep equality on parsed JSON rather than comparing strings. If byte-exact replay were ever required — to re-sign a webhook payload, say — the column would have to be text.

    Hold expiry

    ▾
    available → held → booked / released, with expiry as a reading rule rather than a transition.

    The rule

    A hold is expired when status = 'active' AND expires_at < now(). That is it. Nothing deletes it; nothing rewrites the seat row.

    Why it is correct

    No query anywhere trusts seats.status on its own.

    Reads go through a view, which is the single place the rule is written — so the seat map, seats_left and admin stats can never drift apart:

    backend/app/schema.sql:118–130 — seat_effective
    CREATE OR REPLACE VIEW seat_effective AS
SELECT s.id, s.event_id, s.label, s.row_idx, s.col_idx, s.hold_id,
       CASE
           WHEN s.status = 'held'
                AND h.status = 'active'
                AND h.expires_at < now()
           THEN 'available'
           ELSE s.status
       END AS status
FROM seats s
LEFT JOIN holds h ON h.id = s.hold_id;

    Writes re-check the same condition inside the claim, under a row lock — the OR (status='held' AND hold_id IN (…expired…)) branch of CLAIM_SEATS_SQL. So the decision to reuse an expired seat is made atomically with taking it, not before.

    An un-swept expired hold therefore cannot cause a wrong answer. It can only leave a stale row in the table.

    Table growthRows linger until the seat is reclaimedBounded

    The trade-off is honest and it is visible: /admin shows expired_holds rather than hiding it. At much larger scale I would add a nightly DELETE FROM holds WHERE status='active' AND expires_at < now() - interval '1 day' — for housekeeping, not correctness. That distinction is the whole answer.

    Proved by

    • test_expired_hold_releases_its_seat_to_another_user — and it asserts that the seats row still says held with the old hold_id, so you can see that nothing swept it.
    • test_confirming_an_expired_hold_is_410
    • test_expired_hold_does_not_block_the_users_next_hold — the one-hold-per-user rule must respect expiry too, or a user whose hold timed out would be locked out of the event.
    • test_expired_holds_are_counted_in_admin_stats

    The clock

    The sale gate is now() >= sale_opens_at evaluated in Postgres, so a client clock can never open a sale early. The countdown must therefore tick against the same clock: the frontend fetches /api/time once, stores offset = server − client (charging half the round trip to the response), and adds it to Date.now() forever after. Without that, a laptop five minutes fast shows “On sale” while every attempt returns 403 — a bug that is invisible on a correctly-synced developer machine. /api/time is the one endpoint that must never be cached.

    9.1 — Process model: worker_processes, worker_connections

    nginx/nginx.conf:27–60
    worker_processes auto;
error_log /dev/stderr warn;
events { worker_connections 1024; }
    DoesOne master reads the config and binds the ports; one worker per CPU core actually serves traffic. A worker is single-threaded and event-driven — it holds thousands of sockets in an epoll set and is woken only for the ones with data ready.
    Why hereA flash sale is mostly idle connections — browsers with a seat map open, polling. The event model makes 1,000 idle connections cost a few MB instead of 1,000 threads.
    BreaksToo few connections → Nginx logs “worker_connections are not enough” and drops them, visible as a rising accepts − handled gap. Give a worker a blocking task and that worker stalls for every connection it holds.
    Proofdocker compose exec nginx sh -c 'nproc; ps -o args | grep -c "worker process"' → 12, 14 (12 workers + master + grep)
    MistakesForgetting a proxied request costs two connection slots. And on this image, error_log /dev/stderr is mandatory: we mount a volume over /var/log/nginx, which destroys the image's error.log → /dev/stderr symlink, so docker compose logs nginx would be silent.
    Why not more workers than cores?
    They would just contend for CPU. The workers are not blocking on I/O — that is the whole point of the event model — so there is no idle time for an extra worker to fill. auto is right unless you are pinning workers to cores for NUMA reasons.

    9.2 — Load balancing, and the per-worker trap found while building

    nginx/nginx.conf:303–356 — upstream api_backend
    upstream api_backend {
    // SHARED LOAD-BALANCER STATE -- NOT OPTIONAL WITH MULTIPLE WORKERS
    zone api_backend 64k;

    // least_conn;   # when request cost varies a lot
    // ip_hash;      # sticky sessions -- we need none

    server api1:8000 max_fails=2 fail_timeout=10s;
    server api2:8000 max_fails=2 fail_timeout=10s;
    server api3:8000 max_fails=2 fail_timeout=10s;

    keepalive 32;
}
    DoesRound robin (the default — there is no round_robin; directive to see) across three replicas, with the rotation counter and the failure counters in 64 KB of shared memory.
    Why hereRound robin is correct because the replicas are stateless — JWT auth, all state in Postgres. No sticky sessions needed. ip_hash would be a downgrade: it would pin a whole NATed office to one replica for no benefit.
    BreaksThis is the bug I actually hit. Without zone, the round-robin position and max_fails counters live in each worker's private memory. With 12 workers that is 12 counters all starting at api1 — so 12 separate browser connections all got api1 and load balancing looked completely broken. It also means worker 7 marking api2 as down teaches the other 11 workers nothing.
    Proof

    When would least_conn actually be better?

    How would you add a fourth replica?

    9.3 — Upstream keepalive needs two extra headers

    nginx/snippets/proxy-headers.conf:20–21
    proxy_http_version 1.1;
proxy_set_header Connection "";
    DoesMakes the keepalive 32 pool in the upstream block actually work.
    Why hereAt ~400 seat-map polls/second, a TCP handshake per request is 400 extra connection setups per second and eventual ephemeral-port exhaustion.
    BreaksSilently. By default Nginx talks to upstreams with HTTP/1.0 and sends Connection: close, so the pool is never used. Nothing errors. You just quietly pay a handshake per request and pile up sockets in TIME_WAIT. This is the single most commonly missed pair in an Nginx config.
    Proofdocker compose exec nginx grep -nE 'proxy_http_version|Connection' //etc/nginx/snippets/proxy-headers.conf. Indirectly: /nginx_status showed accepts 19 against requests 194 — 19 connections carrying 194 requests is keepalive working on the client side; the upstream side is the same mechanism.
    MistakesSetting keepalive 32 and stopping there. Also: keepalive is an idle-connection cache size, not a connection limit.
    Why does the Connection header have to be emptied?
    Because Connection is a hop-by-hop header. Nginx forwards the client's one by default, and a browser sending Connection: close would then close our pooled upstream connection too. Setting it to the empty string removes it, so the upstream connection's lifetime is ours to manage.

    9.4 — Passive health checks and failover

    nginx/nginx.conf:329–344, 360–384

    DoesAfter 2 failures within 10 s a server is marked unavailable for 10 s, then one request is let through to see if it recovered. A failed attempt is retried on the next server.

    9.5 — POSTs are never retried never add non_idempotent

    nginx/nginx.conf:381
    proxy_next_upstream error timeout http_502 http_503 http_504;
#                    ^ no `non_idempotent`.  ^ no `http_500`.
    DoesTwo absences are the point. By default Nginx only replays requests it considers safe to replay — GET, HEAD, PUT, DELETE — and never POST/PATCH/LOCK.
    Why hereA timed-out-but-actually-succeeded POST /api/holds/{id}/confirm, replayed, is two bookings for one payment. And http_500 is excluded because a 500 means the request reached the app and may have committed.
    BreaksAdding non_idempotent to that list turns a transient network blip into a silent double booking. There is no error, no log line that looks wrong, and the user is charged twice.
    Proofgrep -n 'non_idempotent' nginx/nginx.conf → three hits, all comments. scripts/verify.sh fails the run if it ever appears outside one. And §9.4 proves retries are active for GETs ("504, 200"), so the only thing standing between a POST and a replay is this rule.
    Scope noteThis is a configuration guarantee backed by Nginx's documented default and the absence of the flag — not an end-to-end experiment. Reproducing “POST times out after the backend committed” reliably needs a fault-injection hook the app does not have. I say that rather than overclaiming.
    So how do you handle a POST that times out?
    The user retries, and their retry carries the same Idempotency-Key. If the original had committed, the key row exists and they get the original response back — one booking. That is the whole division of labour: Nginx never manufactures a duplicate; the app absorbs the ones Nginx cannot prevent.

    9.6 — Rate limiting: the leaky bucket

    Each key gets its own bucket. rate is the drain speed, burst the depth, nodelay whether queued drops are served immediately.
    nginx/nginx.conf:194–232
    limit_req_zone $binary_remote_addr zone=api_ip:10m        rate=20r/s;
limit_req_zone $binary_remote_addr zone=auth_ip:10m       rate=5r/m;
limit_req_zone $http_authorization zone=booking_user:10m rate=2r/s;
limit_conn_zone $binary_remote_addr zone=conn_ip:10m;

limit_req_status  429;
limit_conn_status 429;
    DoesThree independent buckets per key, plus a concurrent-connection cap.
    Why 429Both default to 503, which is a lie: 503 means “the server is broken”, 429 means “you are going too fast, and here is how long to wait”. A client library retries a 429 sensibly and gives up on a 503.
    Why binary$binary_remote_addr is 4 bytes for IPv4 vs up to 15 bytes of text — purely to fit more keys in the same 10 MB (~160k keys).
    Proof 
    $ 120 rapid GET /api/time
     75 200
     45 429

$ the 429 itself:
HTTP/1.1 429 Too Many Requests
Content-Type: application/json
Retry-After: 1
Cache-Control: no-store
X-Content-Type-Options: nosniff        ← all 6 security headers present
… (5 more)

{"error":{"code":"rate_limited","message":"Too many requests, please slow down","retry_after":1}}
    MistakesLeaving the status at 503. Omitting nodelay and wondering why the page feels slow instead of erroring. And forgetting limit_req is not additive across levels — see the next card.
    Where do the 429s go? Do they hit the backend?
    No. Nginx answers them entirely itself, from the @rate_limited named location. That is the point — under attack, the expensive Python process never sees the traffic. In the edge-mode load test, 163 of 300 requests were stopped this way and never reached a replica.
    What happens when the 10 MB zone fills up?
    Nginx evicts the least-recently-used entries, and if it still cannot allocate it returns 503 for that request and logs it. 10 MB holds roughly 160k IPv4 keys, far more than this app will ever track — but it is a real consideration for the per-token zone, where each key is a few hundred bytes of JWT and the capacity drops to ~25k.

    9.7 — Login: 5 per minute, not per second

    BreaksWithout it, an attacker gets 20 password guesses per second per IP for free, and saturates three replicas' CPU doing it.

    No, and I would say so unprompted. It stops the naive case. A distributed credential-stuffing attack rotates IPs and walks straight past it.     9.8 — Per-token booking limit my favourite

    nginx/nginx.conf:217 (zone), 687–696 (location)
    limit_req_zone $http_authorization zone=booking_user:10m rate=2r/s;

location /api/holds {
    limit_req  zone=booking_user burst=5 nodelay;
    limit_req  zone=api_ip       burst=40 nodelay;
    limit_conn conn_ip 50;
    …
}
    DoesKeys the bucket on the whole Authorization header, so each JWT gets its own bucket.
    Why hereA per-IP booking limit is useless when 400 students share one college NAT — they would throttle each other — and too loose when one person scripts 50 attempts from one laptop. Per-token gets both right. A prefix match covers /api/holds, /{id}, /{id}/confirm and the DELETE in one block, so the limit cannot be forgotten on one of them.
    Proof 
    token A — 12 rapid authenticated requests:
      6 404     ← got THROUGH (404 = the uuid does not exist)
      6 429     ← rate limited

      5 404     ← all through. Its own bucket.
    That is the whole argument in one measurement.
    SubtletyA request with no Authorization header produces an empty key, and Nginx does not count empty keys at all — the entry is skipped. So anonymous traffic slips past this zone entirely. That is exactly why api_ip is also applied here, and why the backend 401s an unauthenticated POST regardless. Three layers, each covering the others' gap.
    CostThe key is a few hundred bytes of JWT, so a 10 MB zone holds ~25k tokens instead of ~160k IPs. A production system would validate the JWT at the edge with auth_request and key on a short user id instead — listed as a stretch goal.
    Can a user dodge this by getting a new token?
    Yes, in principle — log in again and you have a new key. But logging in is itself limited to 5/minute per IP by auth_ip, so token rotation is rate-limited by construction. That is the layering working: you cannot cheaply acquire the thing you would need to cheat.

    9.9 — Microcaching: the 400× win

    nginx/nginx.conf:278–284, 552–596
    proxy_cache_path /var/cache/nginx/api levels=1:2 keys_zone=api_cache:10m
                 max_size=100m inactive=10m use_temp_path=off;

location ~ ^/api/events/[0-9]+/seats$ {
    proxy_cache       api_cache;
    proxy_cache_valid 200 1s;
    proxy_cache_methods GET HEAD;

    // *** THE THUNDERING HERD FIX ***
    proxy_cache_lock          on;
    proxy_cache_lock_timeout  2s;

    proxy_cache_use_stale updating error timeout http_502 http_503;
    proxy_cache_background_update on;

    add_header X-Cache-Status $upstream_cache_status always;
}
    The problemEvery open seat map polls every ~2.5 s. 1,000 viewers ≈ 400 requests/second, all asking the identical question, all hitting Postgres. Three uvicorn replicas would spend their entire capacity on a question whose answer barely changes.
    The fixCache it for one second. 400 req/s collapses to ~1 backend request/second per event, and users still see a map at most 1 s old.
    Why safeBecause the seat map is only ever a hint. Ownership is decided exclusively by the conditional UPDATE in Postgres. The worst case: a user clicks a seat someone just took and gets a clean 409 that highlights it and refreshes the map. That is a handled outcome, not a correctness failure. We traded one second of visual freshness for a 400× capacity win, and the “never two owners” invariant was never involved in the trade.
    BreaksWithout proxy_cache_lock, the instant a 1-second entry expires all waiting pollers are simultaneously declared misses and forwarded at once — a stampede every second, worse than no cache at all. With it, one request refills and the rest wait. use_stale updating + background_update go further: serve the stale copy instantly and refresh behind, so nobody waits at all.
    Proof 
    $ 60 parallel GETs of the seat map
     58 X-Cache-Status: HIT
      2 X-Cache-Status: STALE
      0 MISS                     ← no backend request at all

$ a cached response in Nginx's own access log:
{"request_uri":"/api/events/1/seats","status":200,
 "upstream_addr":"",              ← EMPTY. No backend was contacted.
 "upstream_cache_status":"STALE"}
    MistakesCaching without cache_lock. Caching an endpoint that varies by caller. Measuring backend load from the Nginx log — background cache refreshes do not get their own access-log line, so that undercounts; count it on the backend side instead.
    Why 1 second for the seat map but 2 for the event list?
    seats_left is the only thing that moves on the list page and it is not a live dashboard. The seat map is what a user stares at while deciding, so it gets the tightest window that still collapses a storm. Both are arbitrary in the sense that any sub-5-second value works; what is not arbitrary is that they are short — the value of a microcache is almost entirely in the first second.
    What is in the cache key, and why does that matter?
    The default is $scheme$proxy_host$request_uri — it does not include the Authorization header. That single fact decides what may be cached: only responses that do not depend on the caller. It is also why backend/tests/test_edge_contract.py asserts that the cacheable endpoints return identical bytes with and without a token — so the promise the cache relies on is tested, not assumed.

    9.13 — Security headers and the add_header inheritance trap the classic

    add_header is NOT additive across configuration levels.

    • a location with no add_header of its own inherits the whole set from its parent;
    • a location that defines even one inherits none of them.

    So the moment a location adds X-Cache-Status, it silently loses every security header. They do not merge — the nearest level with any add_header wins outright.

    FixOne snippet, included explicitly in every location — even ones that look like they would inherit. Four locations here add their own headers (/assets/ and = /index.html add Cache-Control; the three cached API locations add X-Cache-Status), and every one of them would have been stripped bare.
    alwaysMeans “send this even on 4xx/5xx”. Without it a 429 or a 502 comes back with no security headers at all — and error pages are exactly what an attacker sees most.
    Proof 
    path                          security-headers   own-headers
/api/events/1/seats                  6                1
/api/events                          6                1
/assets/index-*.js                   6                1
/index.html                          6                1
/nginx_status                        6                0
/api/health                          6                0
… and on a 429 response:               6
6/6 everywhere, INCLUDING the four that define their own.

    HSTS, and why it is dangerous on localhost

    nginx/nginx.conf:166–170 + snippets/security-headers.conf:78
    map $scheme $hsts_header {
    default "";
    https   "max-age=300";
}
// in the snippet:
add_header Strict-Transport-Security $hsts_header always;

    HSTS tells the browser “never speak plain HTTP to this host again”, and the browser remembers. A long max-age on localhost would pin every future project you run on localhost to HTTPS, curable only via chrome://net-internals/#hsts. So: max-age is deliberately 300 s, and the map trick means Nginx skips an add_header whose variable is an empty string — letting one shared snippet live in both the HTTP and HTTPS server blocks while emitting HSTS only on HTTPS.

    Measured: 0 HSTS headers over http://localhost:8080, present over https://localhost:8443. On Plan B the same map keys on $http_x_forwarded_proto instead, because Render terminates TLS and $scheme is http there.

    CSP

    default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self' — a strict same-origin policy, which is only possible because this app has no CDN, no external fonts and no third-party analytics.

    • script-src 'self' means no inline <script> and no eval. A Vite production build emits an external module script, so it works; npm run dev would need 'unsafe-inline' for HMR, which is why dev is proxied through Vite rather than Nginx.
    • style-src 'self' does not break React's style={{…}} props — React writes those through the CSSOM (element.style), which CSP does not police. It only blocks literal style="" attributes in markup. Verified in Chrome: zero CSP violations in the console.
    How would you catch a missing header automatically?
    scripts/verify.sh counts the six headers on six different paths including the four that define their own, and on a 429. That is the regression test for the trap — if someone adds add_header to a location and forgets the include, the count drops to 0 and the run fails.

    The bugThe obvious way to write that first rule is expires 1y; plus add_header Cache-Control "public, immutable"; — and it is wrong. expires emits its own Cache-Control, so the response went out with two: 
    Cache-Control: max-age=31536000
Cache-Control: public, immutable
    Which one a cache honours is then up to the cache, and immutable may be dropped entirely. I found this by counting headers; the fix is writing the single complete value by hand. verify.sh now asserts the count is exactly 1.
    Why 1 yearVite emits /assets/index-DyMwxtyS.js — the filename changes whenever the content does. That is what makes a one-year cache safe: there is nothing to invalidate, only new names. immutable additionally stops revalidation on a hard refresh.
    index.htmlMust never be cached, or a user with the page open keeps loading the old index-<oldhash>.js forever after a deploy — a 404 or a stale app with no way out but a hard refresh. no-cache means “revalidate every time”, not “do not store”: the browser still gets a cheap 304.

    9.16 — Location precedence (why the ordering works)

    Nginx does not match locations top to bottom. The real algorithm:

    1. location = /exact wins immediately.
    2. The longest location /prefix match is remembered.
    3. Every location ~ regex is tried in file order; the first hit wins and the remembered prefix is discarded.
    4. If no regex matched, the remembered prefix is used.
    RequestMatched byWhy
    /api/events= /api/eventsexact — rule 1
    /api/events/1~ ^/api/events/[0-9]+$regex beats the /api/ prefix
    /api/events/1/seats~ …/seats$listed before the other regex
    /api/holds/x/confirm/api/holdsno regex matches; longest prefix
    /api/bookings/api/the general fallback
    /checkout/abc/lowest-priority prefix → SPA
    MistakesAssuming top-to-bottom. Adding a regex above /api/holds that accidentally matches it and silently removes the per-token limit. ^~ is the escape hatch: it makes a prefix match stop regex checking entirely.
    Why is /api/holds a prefix and not three exact locations?
    Because it covers /api/holds, /api/holds/{id}, /api/holds/{id}/confirm and the DELETE in one block — so the per-token rate limit cannot be forgotten on one of them. Three exact locations would be three places to keep in sync, and the one you forget is the one that gets abused.

    9.18 — One error envelope, including from the edge

    nginx/nginx.conf:743–776
    error_page 429 = @rate_limited;
error_page 413 = @too_large;
error_page 502 503 504 = @upstream_down;

location @rate_limited {
    default_type application/json;
    add_header Retry-After 1 always;
    include /etc/nginx/snippets/security-headers.conf;
    return 429 '{"error":{"code":"rate_limited","message":"…","retry_after":1}}';
}
    WhySo the frontend has exactly one error parser. Without it, a 429 from the edge arrives as an HTML page, response.json() throws, and the user sees “something went wrong” instead of “too many requests, slow down”.
    MatchingEvery error in the system uses {"error":{"code","message"}} — from FastAPI, from Starlette's router, and from Nginx. backend/tests/test_edge_contract.py enforces the app side, including a case found during verification where an unmatched route returned Starlette's default {"detail":"Not Found"}.
    @upstream_downReached only when every upstream attempt failed — all three replicas unreachable, not just one. A single dead replica is invisible because proxy_next_upstream already retried it.

    9.19 — Config quality gates: nginx -t and zero-downtime reload

    Reload 
    $ docker compose cp nginx/nginx.conf nginx:/etc/nginx/nginx.conf
$ docker compose exec nginx nginx -t        # ALWAYS test first
nginx: configuration file /etc/nginx/nginx.conf test is successful
$ docker compose exec nginx nginx -s reload
    The master re-reads the config, starts new workers with it, and tells the old ones to finish their in-flight requests and exit. No connection is dropped.
    Proof400 requests streaming across a reload: 0 dropped (155 × 200, 245 × 429 — and the 429s are the rate limiter doing its job, all of them complete HTTP responses over healthy connections).
    Why test firstA reload with a broken config leaves the old workers running, so the site stays up — but you have no idea the change did not apply. That is the failure mode nginx -t prevents.
    Build-time gateThe Dockerfile runs nginx -t too — but not in the obvious way. Nginx resolves every upstream hostname at config-parse time and aborts with host not found in upstream "api1:8000" if one is unknown. At build time there is no compose network, so a plain nginx -t always fails (I hit this on the first build). Patching /etc/hosts is not an option either — BuildKit mounts it read-only. So the Dockerfile validates a copy with the hostnames sed'd to a literal IP, which still checks every directive, include, regex and certificate path.
    ConsequenceThat same resolve-at-startup behaviour is why docker-compose.yml makes nginx depend_on the three API services. Without it, a cold docker compose up crashes Nginx roughly half the time.
    How do you handle backends whose addresses change at runtime?
    Three options. A resolver directive plus a variable in proxy_pass (set $backend "api"; proxy_pass http://$backend;) makes Nginx resolve per request instead of at startup — at the cost of losing the upstream block's load balancing. Or service discovery that rewrites the config and reloads (Consul-template). Or a platform that gives you a stable virtual IP, like Kubernetes Services. For a fixed set of three replicas, parse-time resolution is simplest and the depend_on handles it.

    Nginx and networking
    What is a reverse proxy, and why do you need one here?
    A reverse proxy sits in front of your servers and speaks for them: the client only ever knows the proxy. Here it buys six things at once — TLS termination in one place, load balancing across three replicas, failover when one dies, rate limiting before traffic is expensive, caching, and one consistent access log. Without it each replica would need its own certificate and public port, and the browser would have to know about three hosts.
    Difference between a forward proxy and a reverse proxy?
    A forward proxy acts for the client — the client configures it, and the server sees the proxy's address (corporate egress proxy, VPN). A reverse proxy acts for the server — the client knows nothing about it and thinks it is talking to the real service. Same mechanism, opposite direction of trust.
    How does Nginx decide which replica gets a request?
    Round robin by default — there is no directive to see, which surprises people. The alternatives are least_conn (fewest active requests; right when request cost varies a lot) and ip_hash (sticky by client IP; the tool you are forced into by stateful backends). I use round robin because the replicas are stateless. Critically, the rotation state must be in shared memory via zone, or each worker rotates independently.
    Explain Nginx's process model.
    One master process reads the config and binds the ports; it spawns one worker per CPU core. Each worker is single-threaded and event-driven — it holds thousands of sockets in an epoll set and is woken only for the ones with data ready. There is no thread per connection, which is why one worker carries ~10k idle connections on a few MB. The corollary: never give a worker a blocking task, because that worker stalls for every connection it is holding.
    Why does upstream keepalive need two extra directives?
    Because by default Nginx talks to upstreams with HTTP/1.0 and sends Connection: close. So keepalive 32 alone does nothing — silently. You need proxy_http_version 1.1 and proxy_set_header Connection "". The failure mode is the dangerous kind: no error, you just pay a TCP handshake per request and eventually run out of ephemeral ports.
    How does microcaching work and when is it safe?
    You cache a response for a very short window — one or two seconds — so a burst of identical requests collapses into one backend call. It is safe exactly when two things hold: the response does not depend on who is asking (because the cache key does not include identity), and brief staleness is tolerable. Both hold for a seat map, because the map is only a hint — ownership is decided in Postgres and a stale click yields a clean 409. Neither holds for /api/bookings, so it is not cached.
    What is the thundering herd, and how do you avoid it?
    When a cache entry expires, every waiting client is simultaneously a cache miss and they all stampede the backend at once. With a 1-second TTL that happens every second — worse than having no cache. proxy_cache_lock on lets exactly one request through to refill while the rest wait; proxy_cache_use_stale updating plus proxy_cache_background_update on go further and serve the stale copy immediately so nobody waits at all.
    Leaky bucket vs token bucket — which is Nginx's and what do the knobs do?
    Nginx's limit_req is a leaky bucket. Each key gets a bucket draining at rate; each request adds a drop. burst is the bucket depth — a small waiting room for a spike. nodelay decides whether queued drops are served immediately or spaced out at rate. Without nodelay a burst of 40 at 20 r/s means the 40th request waits ~2 seconds, which users read as a frozen page; with it they all go at once and then the bucket refuses until it drains. They are nearly equivalent models; the practical difference is that a token bucket naturally allows an initial burst after idle, which burst approximates.
    Why return 429 and not 503?
    They mean different things and clients treat them differently. 503 says “the server is broken” — a client library tends to give up or trip a circuit breaker. 429 says “you are going too fast, and here is how long to wait” — a client backs off and retries. Nginx defaults limit_req_status to 503, which is simply the wrong message, so I set it to 429 and add Retry-After.
    What is the add_header inheritance trap?
    add_header is not additive across configuration levels. A location with no add_header of its own inherits the parent's whole set; a location that defines even one inherits none. So adding X-Cache-Status to a location silently strips every security header from it. The fix is to include the shared snippet in every location explicitly. And always matters separately — without it, headers are omitted on 4xx/5xx, which are exactly the responses an attacker sees.
    How does Nginx choose a location block?
    Not top-to-bottom. First, an exact = match wins immediately. Otherwise it remembers the longest prefix match, then tries every regex in file order — the first regex that hits wins and the prefix is discarded. If no regex matches, the remembered prefix is used. ^~ on a prefix tells it to stop before the regex phase.
    What does “TLS termination” mean and what is the trade-off?
    The proxy decrypts TLS and talks plaintext to the backends. You get one certificate to renew instead of N, no TLS CPU on the app processes, and the proxy can inspect and cache. The trade-off is that the proxy-to-backend hop is plaintext — fine on a private Docker network, not fine in a zero-trust environment, where you would re-encrypt or use mTLS. The backends learn the original scheme from X-Forwarded-Proto.
    Why enable HTTP/2 for this app specifically?
    The seat-map page issues its poll alongside other requests. Over HTTP/1.1 a browser opens up to six connections per origin and head-of-line-blocks within each; HTTP/2 multiplexes everything over one TCP+TLS connection, so the polling costs one connection rather than contending for six. Note the directive form matters: http2 on; is the modern syntax (≥1.25.1) and listen … http2 is deprecated, which is one reason the image tag is pinned.
    What actually happens on nginx -s reload?
    The master re-reads and validates the config, then starts new workers using it and signals the old workers to stop accepting new connections and exit once their in-flight requests finish. No connection is dropped. If the new config is invalid the master refuses and the old workers keep serving — which is why the site stays up but your change silently did not apply, and why you run nginx -t first.
    Concurrency and database
    Walk me through two people clicking the same seat at the same millisecond.
    Both reach different replicas and both open a transaction running the same conditional UPDATE. T1 takes the row lock and writes held. T2's UPDATE reaches the same row, finds it write-locked and blocks — queued, not spinning. T1 commits. T2 wakes and, at READ COMMITTED, Postgres re-reads the new row version and re-evaluates the WHERE clause against it; the row no longer matches, so T2 gets zero rows. The count mismatch raises, the whole transaction rolls back, and the user gets 409 with the conflicting seat ids. Proved by 50 concurrent users on one seat → exactly 1 × 201.
    What is a lost update and why does your design not have one?
    A lost update is read-then-write with a gap: both transactions read “available”, both decide to write, and the second silently overwrites the first's decision. My claim has no gap because the check is the write — the eligibility rule lives in the WHERE clause of the UPDATE. A SELECT followed by an UPDATE has that gap unless the SELECT took FOR UPDATE.
    What isolation level are you running, and why not SERIALIZABLE?
    READ COMMITTED, Postgres' default. It is enough because I am not relying on the snapshot — I rely on row locks plus the WHERE re-evaluation that READ COMMITTED performs after a blocking write commits. SERIALIZABLE would also be correct but every hot seat becomes a serialization failure under a flash sale, so you must write retry logic anyway and throughput falls exactly when you need it most. I would reach for SERIALIZABLE if the invariant spanned multiple rows in a way a single statement could not express.
    What is MVCC, and what is the “recheck” you keep mentioning?
    MVCC means each transaction sees a snapshot of the data; writers create new row versions rather than overwriting, so readers never block writers. The subtlety: at READ COMMITTED, when an UPDATE blocks on a row another transaction is modifying and that transaction commits, Postgres does not just proceed — it re-reads the newly committed version and re-evaluates the statement's WHERE clause against it. That is EvalPlanQual, and it is precisely what makes my conditional UPDATE safe.
    Can your claim deadlock?
    Yes, in principle — two transactions requesting overlapping seat sets could lock rows in opposite orders. Postgres detects the cycle and aborts one with SQLSTATE 40P01. From the client's point of view that is indistinguishable from losing the race, so claim_seats catches DeadlockDetectedError and returns the same 409 rather than leaking a 500. Sorting the seat ids helps but does not control Postgres' scan order, so catching it is the honest answer.
    Optimistic or pessimistic locking — which is this, and when would you flip?
    Pessimistic, effectively: the UPDATE takes a row lock and contenders block. That is right for a flash sale because contention is the normal case, so optimistic retries would become a retry storm. Optimistic locking (a version column, retry on zero rows affected) wins under low contention where blocking would be wasted waiting. The deciding question is always “how often do two writers actually collide?”
    If the SQL is already correct, why the UNIQUE (seat_id)?
    Because the SQL being correct is a property of the code as it is today, and code changes. The constraint makes overselling impossible even if someone later edits holds.py badly. It is also what lets the admin stats endpoint make a meaningful claim: it counts duplicates straight from booking_seats with a query that shares no code with the booking path, and the answer can never be non-zero because the database would not store it.
    Why does ON CONFLICT DO NOTHING make concurrent duplicates safe?
    Because it blocks rather than returning early. Postgres takes a speculative-insertion lock and waits for the conflicting transaction to finish. If that one committed, we get no row back and our next statement — a fresh snapshot, because READ COMMITTED takes one per statement — can see the committed row with its stored response, which we replay. If it rolled back, our insert succeeds and we legitimately do the work. So exactly one caller does the work and the loser waits instead of racing.
    Why is the idempotency record written in the same transaction as the work?
    So that “work done” and “key recorded” are a single atomic fact. In separate transactions there is a window where one is true and the other is not — either the key says done but the booking never committed, or the booking committed and the key did not, which lets a retry do the work twice. One transaction removes the window entirely.
    Why no background job to expire holds?
    Because it would buy no correctness. Every read goes through a view that treats an aged-out hold as available, and the claim re-checks the same condition under a row lock — so the decision to reuse an expired seat is made atomically with taking it. A sweeper would be a worker, a schedule, its own failure modes and a new race against live claims, in exchange for smaller tables. The trade-off I accept is stale rows, and /admin reports the count rather than hiding it. At scale I would add a nightly DELETE for housekeeping, not correctness.
    How do you size the connection pool?
    10 per replica × 3 replicas = 30 Postgres backends, which is comfortable for one node — Postgres backends are processes, so connections are genuinely expensive. The tests raise it to 25 via DB_POOL_MAX so that 50 concurrent hold attempts actually contend in Postgres rather than queueing on pool acquisition, which would make the concurrency test pass for the wrong reason. At scale the next step is PgBouncer in transaction mode — which is why statement_cache_size=0 is already set.
    Where could you have had an N+1 query, and how did you avoid it?
    The tickets list — one query for bookings, then one per booking for its seat labels. I aggregate the labels in SQL with array_agg in a correlated subquery, so it is one round trip. Same pattern for seats_left on the events list, which is a subquery against the seat_effective view rather than a per-event count in Python.
    What indexes does this need and why?
    Four hot queries drive them: the seat map by event (seats(event_id)), the claim by seat id set (the primary key), “do I already hold seats for this event” (holds(user_id, event_id, status)), and my bookings (bookings(user_id)). Plus seats(hold_id) because confirm and release both look seats up by hold. I would check them with EXPLAIN ANALYZE under realistic data before claiming anything stronger — at 200 seats per event, Postgres may well prefer a sequential scan, and that is fine.
    API design
    Why 409 for a taken seat but 410 for an expired hold?
    409 Conflict means “the resource is contested right now” — someone else has it, and the user should pick again. 410 Gone means “this thing no longer exists” — the hold is not contested, it has ceased to be a claim, and its seats are already free for anyone. The distinction matters to the client: 409 highlights specific seats and refreshes the map; 410 sends the user back to pick seats afresh. 422 is reserved for “your request is malformed or contradicts a previous one”, which is where idempotency_mismatch lives.
    Why one error envelope everywhere?
    So the frontend has exactly one parser and switches on a stable machine-readable code, never on human text. The hard part is that errors come from four places — my handlers, pydantic validation, Starlette's router, and Nginx itself. I had to add a StarletteHTTPException handler because an unmatched route was returning {"detail":"Not Found"}, a second shape I found while verifying the edge. Nginx's 429/413/503 pages are hand-written to match.
    Why is Idempotency-Key required rather than optional?
    Because optional-but-honoured leaves the server in a state where a retry is ambiguous, and you only find out when someone is double-booked. Making it mandatory means a client that forgets it gets a 400 at the door — a loud, immediate, cheap failure instead of a silent, expensive, later one. It is the same instinct as making a database column NOT NULL.
    Why a hold at all? Why not just book directly?
    Because payment takes time and the user needs their seats to still be there when they finish. A hold is a short-lived exclusive claim that decouples “I have chosen” from “I have paid”. It is the same two-phase pattern as a reservation with a TTL. The alternative — book first, refund on failure — means taking money for seats you might not be able to honour, and it makes the oversell question worse rather than better.
    Why does DELETE not need an idempotency key?
    Because DELETE is naturally idempotent — releasing an already-released hold is a no-op that still returns 200. The retry is harmless by construction rather than by bookkeeping, so adding a key would be ceremony with no benefit. That is the general rule: spend the idempotency machinery only where the operation genuinely creates something.
    How would you version this API?
    I would not version it until I had to. When I did: URL prefix (/api/v2/…) because it is trivially visible in logs and in Nginx location blocks, which matters here since the cache and rate-limit rules are keyed on paths. Header-based versioning is more elegant but makes the edge config harder to reason about, and in this architecture the edge config is a first-class thing.
    Security
    JWT vs server-side sessions — defend your choice.
    JWT, because statelessness is the property the whole architecture rests on: it is what makes the three replicas interchangeable and plain round robin correct. The honest cost is revocation — a logout or a compromised account stays valid until exp, 24 hours here. The mitigation is a short TTL plus a deny-list (a small Redis set or table of revoked jti) checked on each request, which gives back most of the benefit of sessions without the affinity. If I needed instant revocation more than I needed statelessness, I would use sessions and accept ip_hash or a shared session store.
    JWT in localStorage — is that not an XSS risk?
    Yes, and I would not pretend otherwise: any script running on the origin can read it. The alternative is an httpOnly, Secure, SameSite cookie, which XSS cannot read — but that brings CSRF handling, and it would stop Nginx caching any response carrying Set-Cookie, which matters here. I mitigated rather than eliminated: a strict same-origin CSP with no unsafe-inline, which blocks the injected script in the first place, plus connect-src 'self' so an injected script cannot exfiltrate to another host. It is listed in the limitations.
    Why scrypt, and what makes a good password hash?
    A good password hash is deliberately slow and ideally memory-hard, so an attacker with a stolen database and a GPU farm cannot brute-force it cheaply. scrypt is memory-hard and it is in the Python standard library, so there is no C toolchain in the image. I store the parameters alongside the hash (scrypt$n$r$p$salt$hash) so they can be raised later without invalidating existing passwords, and verification uses hmac.compare_digest so comparison is constant-time. argon2id is the current best practice and is what I would use in production.
    You write raw SQL — what about injection?
    Every query uses asyncpg's numbered placeholders ($1, $2) and values are passed as parameters, never interpolated into the string. The driver sends them out of band, so there is no string for an attacker to break out of. The one place I build SQL dynamically is a shared column list (_EVENT_COLS), which is a constant in the source and contains no user input. “Raw SQL” means hand-written, not string-concatenated.
    Walk me through your CSP.
    default-src 'self' with script-src 'self' — no inline scripts, no eval — plus connect-src 'self' so an injected script cannot phone home, frame-ancestors 'none' against clickjacking, and base-uri/form-action 'self'. It is only possible to be this strict because the app has no CDN, no external fonts and no third-party analytics. Two subtleties: a Vite production build emits an external module script so it works, while npm run dev would need unsafe-inline for HMR; and style-src 'self' does not break React's style={{}} props because React writes through the CSSOM, which CSP does not police. Verified in Chrome — zero violations.
    How do you avoid account enumeration?
    “No such user” and “wrong password” return a byte-identical 401 — there is a test asserting the two responses are equal. Password comparison is constant-time via compare_digest. The remaining leak is timing: a missing user skips the scrypt hash and so answers faster. Closing that properly means hashing a dummy password on the miss path, which I have not done — it is a real gap and I would rather name it than claim the endpoint is perfect.
    Your secrets are in the repo.
    They are, and they are clearly marked DEV-ONLY in config.py and overridden in compose. For a demo that anyone should be able to git clone and run with one command, a working default beats a setup step. In production they come from a secret store, injected as environment variables, and the JWT secret needs to be rotatable — which means accepting two keys during a rotation window, something the current code does not do.
    Frontend
    Why polling instead of WebSockets or SSE?
    Polling plus a 1-second microcache gives near-live updates with no connection state, no reconnect logic and no cross-replica fan-out problem — and the edge absorbs the cost, which I measured. WebSockets would need Redis pub/sub because a socket lives on one replica while the write lands on another. SSE is the middle ground — one-way, works over plain HTTP/2, simpler than WebSockets — and is what I would try first if I wanted push without full duplex. The deciding factor was that I could show the poll costing the backend almost nothing.
    What happens to your polling when the tab is backgrounded?
    It stops. usePoll watches document.visibilityState and clears the timer when the tab is hidden, then refreshes immediately on return so the user does not stare at a stale map. Nginx's cache would absorb those requests anyway, but not making them is strictly better — otherwise a thousand open-but-hidden tabs are a thousand pointless requests every 2.5 seconds.
    Where does the frontend generate its idempotency key?
    Once per user action, not per HTTP attempt — that is the whole point. useAction holds the key in a ref, reuses it for any retry of that action, and only mints a new one after the action succeeds, because at that point the next click is a genuinely new action. It also refuses to fire while one is in flight, which is the double-click guard.
    Why not just use the client clock for the countdown?
    Because the sale gate is evaluated in Postgres with now(), so the UI must count down to the same clock. A user whose laptop is five minutes fast would see “On sale” and get 403 on every attempt — a bug that is completely invisible on a correctly-synced developer machine. The frontend fetches /api/time once, charges half the round trip to the response, and stores the offset.
    How is the seat map accessible?
    Every seat is a real <button>, so it is in the tab order and works with Enter/Space with no extra JS. Each has an aria-label reading “Row C, seat 7, available” — the status is in the label, not only in the colour. Each state also carries a distinct glyph (· ✕ ▣ ✓) so it is readable in greyscale or with colour vision deficiency. Taken seats are disabled, which both greys them and removes them from the tab order. Toasts are in an aria-live region so a 409 is announced rather than appearing silently.
    How did you handle CORS?
    I did not have to, and that is the point. Nginx serves the React bundle and proxies /api from the same origin, so every fetch is a relative path, there are no preflight requests, and there is no CORS config to get wrong. npm run dev breaks that property, so Vite proxies the same relative paths to the running stack — the app code never knows the difference.
    Docker and deployment
    Why a multi-stage Docker build?
    Node is needed to build the React app but the output is static files, so Node never ships. The final image is ~50 MB of Nginx plus HTML instead of ~1.1 GB with node_modules. Smaller image, faster pulls, and a much smaller attack surface — there is no package manager or toolchain in the thing that faces the internet.
    How do you guarantee startup order?
    With conditions, not sleeps. Postgres has a pg_isready healthcheck — “running” is not the same as “accepting connections”, because the entrypoint starts the server, stops it to run init scripts, and starts it again. migrate waits for service_healthy, the replicas wait for service_completed_successfully on migrate, and nginx depends on the replicas because it resolves upstream hostnames at config-parse time and refuses to start if one is unknown.
    Why can't you just run nginx -t in the Dockerfile?
    Because Nginx resolves every upstream hostname at config-parse time and aborts with “host not found in upstream”. At build time there is no compose network, so api1 does not exist. Patching /etc/hosts does not work either — BuildKit mounts it read-only. So I validate a copy of the config with the hostnames sed'd to a literal IP, which still checks every directive, include, regex and certificate path; the only thing skipped is the DNS lookup, which is exactly the part that cannot work there.
    What is the envsubst trap on Plan B?
    envsubst with no argument substitutes every $name it finds — including Nginx's own $host, $remote_addr, $binary_remote_addr. I captured the counter-demonstration: correctly rendered you get limit_req_zone $binary_remote_addr zone=api_ip:10m; unrestricted you get limit_req_zone zone=api_ip:10m — the key variable gone. And it still parses, which is what makes it dangerous: a running site where every visitor shares one rate-limit bucket and the logs have no client IPs. The fix is the quoted argument envsubst '${PORT}', plus nginx -t immediately after.
    Behind a cloud load balancer, how do per-IP rate limits still work?
    They do not, unless you fix it. Every request arrives from the platform's proxy, so $remote_addr is that proxy and the whole internet shares one bucket. real_ip_header X-Forwarded-For plus real_ip_recursive on rewrites $remote_addr to the real client. The critical part is set_real_ip_from: XFF is a client-supplied header, so Nginx must only trust it when the request actually came from the known proxy range. Setting that to 0.0.0.0/0 would let anyone spoof their IP and walk straight past the limiter.
    Why is there no restart policy on the API services?
    So docker compose stop api2 stays stopped during the failover demo — a restart policy would bring it straight back and silently undo the thing I am demonstrating. It is a demo-specific choice and the compose file says so in a comment; production would use unless-stopped.
    Scaling
    What breaks first at 100× traffic?
    Postgres write contention on the hot seats — not Nginx, not the app. Reads are already solved: the microcache makes backend load independent of crowd size, so 100× viewers is roughly the same backend load, and Nginx is nowhere near its limits (accepts − handled is 0). But writes cannot be cached. 100× the rush means 100× the transactions queuing on the same few hundred rows, and they serialise by construction — that is the point. The claim is fast (p50 438 ms at 300 concurrent), but at 30,000 concurrent buyers the lock queue and then the connection pool become the wall.
    In what order would you fix it?
    (1) Read replicas, and move the seat map off the primary. (2) Shard by event — events never interact, so it is the natural partition key and it scales almost linearly. (3) A virtual waiting room in front of the sale, so admission is throttled rather than requests being rejected — much better UX than 429s under a genuine stampede. (4) Only then consider pre-reserving seat ranges per worker, which trades utilisation for far less contention. What I would not do is relax the locking.
    How would you go multi-region?
    Carefully, because seat booking is a strongly-consistent workload and multi-region writes fight that directly. The approach that actually works is partitioning by geography rather than replicating globally: an event belongs to a region and its writes happen there, with the seat map read from local replicas and the SPA served from a CDN everywhere. Users booking a London show hit the EU primary regardless of where they are — you accept cross-region write latency for the minority rather than giving up consistency for everyone. What I would avoid is multi-primary with conflict resolution: there is no sensible way to merge two people who both booked seat C7.
    Your rate limits are per Nginx node. What happens with ten nodes?
    The effective limit multiplies by ten, which may be fine if you size for it — divide the intended limit by the node count and accept the imprecision from uneven balancing. If you need real global limits, they move to a shared store: Redis with a sliding window, a sidecar like Envoy's ratelimit service, or the cloud load balancer's own WAF rate limiting. That is a genuine distributed-systems trade: precision versus a network round trip on every request.
    How would you invalidate the cache early if you needed to?
    With a 1-second TTL you mostly do not need to — waiting is cheaper than any invalidation scheme. If I did, open-source Nginx has no proxy_cache_purge (that is Plus or the third-party ngx_cache_purge module), so the practical options are: delete the cache file by computing its key hash, or add a cache-busting query parameter from the app when something important changes. The honest answer is that choosing a TTL short enough that invalidation is unnecessary is usually the better engineering.
    What would you monitor in production?
    Four technical numbers and one business one. Technical: 429 rate by zone (a spike is either an attack or a limit set too tight), cache hit ratio (a drop means the backend is about to feel it), upstream_response_time percentiles, and accepts − handled above zero. Business: seats_in_two_bookings must be flat zero forever — that is the alert that means something is deeply wrong. Shipped via nginx-prometheus-exporter against stub_status plus the JSON access log into Loki.
    About you
    Why did you build this?
    I wanted one project where the infrastructure was not an afterthought. Most portfolio apps put a proxy in front because a tutorial said to, and could not tell you what any directive does. I picked a flash sale because it forces both halves to be real at once: a traffic spike that only the edge can absorb, and a contention spike that only the database can resolve. That gave every Nginx directive a reason to exist in this app, which is the difference between configuration and copy-paste.
    What was the hardest part?
    Convincing myself the concurrency was actually right rather than just passing. It is easy to write a test that cannot fail — mock the database and 50 concurrent users trivially produce one winner. Making it real meant running against actual Postgres, raising the pool so requests contended in the database instead of queueing on pool acquisition, and building a load-test mode that bypasses Nginx entirely so the rate limiter could not throttle the race away and make a broken implementation look correct.
    What would you do differently?
    Three things. I would write verify.sh earlier — I found six measurement bugs in it, and every one meant a check had been lying to me. I would have built the ops dashboard sooner, because being able to see which replica served what turned debugging the round-robin problem from guesswork into a two-minute diagnosis. And I would add one fault-injection hook so I could test the POST-retry behaviour end to end instead of arguing it from configuration.
    Tell me about a bug you found.
    Round robin looked completely broken — thirty requests, all to api1. The tell was that on a single reused keepalive connection the same config cycled api3, api1, api2 correctly. Per-connection broken but per-worker fine means the state is per worker: with worker_processes auto I had twelve workers, each with its own counter starting at api1. One line fixed it, zone api_backend 64k, which also means the workers now share failure state — without it, one worker marking api2 down teaches the other eleven nothing. I like it because the fix was trivial and the diagnosis was not.
    How did you use AI tools, and how did you verify the code?
    Heavily — for scaffolding, for a first draft of the Nginx config, and as something to argue with about trade-offs. I think that is the normal way to work now, and the interesting question is what I did to be able to stand behind the result.

    I made the machine prove every claim: nothing in the docs is from memory, every number came from a command I ran, and the transcripts are committed. When the microcache needed a backend-contact count I did not trust Nginx's log — background cache refreshes are not logged there — so I counted it on the backend side instead, and the number changed from 1 to 22.

    The verification caught real bugs, including in itself: round robin, two Cache-Control headers on assets, unmatched routes returning the wrong error shape, and six measurement bugs in my own script — the most embarrassing being 120 parallel curl processes losing most of their output to an append race, so a check reported 31 results out of 120 and I believed it until the numbers stopped adding up.

    And where I could not explain something, I cut it. That is why there is no ORM and no Redis. The honest summary: the assistant made me much faster at producing code and made no difference at all to whether the code was right. That part came from running it.
    What would you push back on if a tech lead asked you to change something here?
    Adding non_idempotent to proxy_next_upstream. It looks like a reliability improvement — fewer errors shown to users — and it is actually a correctness bug: a timed-out-but-succeeded payment gets replayed. I would ask what problem we are solving, and if it is “users see errors during deploys”, the answer is graceful shutdown and connection draining, not replaying writes. I would want that one in writing.
    What shortcuts did you knowingly take?
    Dev secrets in the repo so a clone runs with one command. No payment integration — “Pay” is a button, though the idempotency machinery is exactly what a real provider's webhook needs. No frontend tests; the UI is verified by hand and by a browser walkthrough. One Nginx node, so the gateway is the single point of failure in Plan A — the three replicas protect against an app crash, not against the edge dying. All of those are in the limitations section rather than buried.

    Scaling to production

    ▾

    In order, with the reason each one comes where it does.

    #ChangeWhy this early / late
    1Secrets out of the repo, JWT secret rotatable (accept two keys during a window) First because it is the only item that is currently wrong rather than merely absent. Everything else is a missing feature; this is a live exposure.
    2Managed Postgres with automated backups and PITR Second because the database is the single source of truth and currently has no backups. Losing it loses every booking. Nothing else matters if this fails.
    3Real certificates (ACME), HSTS to a year with includeSubDomains Third because it is cheap and it is the difference between a site people trust and a browser warning.
    4Remove the demo affordances — X-Upstream, open /nginx_status, /api/admin/loadtest-users, the reset endpoint Fourth because they are small, known, and each is a real leak. Do them before anyone is looking.
    5Observability — Prometheus + Grafana, the four edge metrics plus the oversell alert Before scaling anything, because you cannot make a scaling decision without numbers. This is the step that turns opinions into measurements.
    6Read replicas, seat map served from them The first genuine scaling move, and the highest leverage: it removes the heaviest read from the primary while the primary keeps doing the thing only it can do.
    7Multiple Nginx nodes behind a cloud LB, with real_ip configured Removes the single point of failure. Immediately breaks per-node rate limiting — which is why it comes with…
    8Shared rate limits (Redis sliding window, or the cloud LB's WAF) …this, directly after. Doing 7 without 8 silently multiplies every limit by the node count.
    9Active health checks — Nginx Plus, or move the edge to Envoy/HAProxy Only now, because passive checks plus retries already hide a dead replica from users. This improves detection latency, not availability.
    10Shard by event When one primary is genuinely the wall. Events never interact, so it is the natural partition key and scales almost linearly.
    11Live seat updates — WebSocket + Redis pub/sub Last of the architectural changes, because polling plus a microcache already delivers ~90% of the benefit and I can prove the poll costs almost nothing. Add it when you need sub-second accuracy, not before.
    12Virtual waiting room When the sale is big enough that rejecting people with 429 is worse UX than admitting them in order. This is a product decision as much as a technical one.
    —Hold-expiry housekeeping (nightly DELETE), token deny-list, argon2id, real payments Independent of scale; schedule them whenever. Note the sweeper is for table size, never correctness.

    The live-updates design, if asked

    • A WebSocket endpoint per event; the browser subscribes instead of polling.
    • When a claim or confirm commits, the replica publishes a small delta {seat_id, status} to a Redis channel keyed on the event.
    • Every replica subscribes and fans the delta out to its own sockets.

    Redis is required because a connection lives on one replica while the write may land on a different one — something has to be shared.

    The real costs, which is what the question is about: Nginx needs proxy_http_version 1.1 plus Upgrade/Connection headers and a much longer proxy_read_timeout on that location; load balancing stops being stateless for those connections; the client needs reconnect-with-resync, because a dropped socket means missed deltas and it must fall back to a full snapshot; and you have added a component whose failure mode is “the UI silently stops updating”, which is worse than an obvious error.

    Known limitations

    ▾

    Knowing these is worth more than hiding them. If an interviewer finds one you did not mention, it reads as a gap; if you name it first, it reads as judgement.

    Security

    • JWT_SECRET and the Postgres password are dev defaults committed to the repo. Marked DEV-ONLY and overridden in compose, but they are not secrets.
    • No token revocation. Logout clears the browser's copy; the token stays valid until exp (24 h).
    • JWT in localStorage — XSS would expose it. The strict CSP mitigates, it does not eliminate.
    • /nginx_status is unauthenticated. Deliberate for the demo; the allow/deny pair is in the config, commented.
    • X-Upstream leaks internal IPs and the replica count.
    • GET /api/admin/loadtest-users would not ship. Scoped to lt% and returns no hashes, but it exists only so the load test can mint JWTs.
    • Login timing leak — a missing user skips the scrypt hash and answers faster. Closing it means hashing a dummy password on the miss path.
    • No account lockout, email verification, password reset or MFA.
    • Rate limits are per Nginx node. Two nodes = double the effective limit.

    Correctness and data

    • Expired holds are never deleted. Correct, but the tables grow. /admin shows the count.
    • No audit log — you cannot reconstruct who held what, when.
    • jsonb normalises key order, so an idempotent replay is semantically but not byte-identical. Fine for JSON; not fine if a client needed to re-verify a signature over exact bytes.
    • No payment integration. “Pay” is a button.
    • Single Postgres, no replica, no backups in this setup.
    • Seat maps cap at 10 × 20. A stadium needs pagination or a different representation — 50,000 seats as one JSON blob is not viable.

    Operations

    • Single Nginx node — the single point of failure in Plan A. The three replicas protect against an app crash, not against the gateway dying.
    • Self-signed certificate, so every visitor sees a warning.
    • No metrics backend — /ops reads stub_status and the access log; no Prometheus, no retention, no alerting.
    • Logs are not rotated — the access log grows until the volume is pruned.
    • docker compose is not an orchestrator: no rolling deploys, no autoscaling.
    • Plan B's free tier sleeps, has no shell (so no failover demo) and has an ephemeral disk.

    Testing

    • The “POSTs are never retried” property is a configuration guarantee backed by Nginx's documented default and the absence of the flag, demonstrated alongside proof that retries are working for GETs. It is not an end-to-end experiment — that needs a fault-injection hook the app does not have.
    • The load test runs from one machine and one source IP, so per-IP limits dominate at high viewer counts. The tool reports that explicitly rather than letting it look like a cache failure.
    • No frontend unit tests. The UI is verified by hand and by the browser walkthrough in DEMO.md.
    • All measurements are from one laptop, not a controlled environment. Orders of magnitude, not benchmarks.

    Glossary

    ▾
    TermMeaning
    Reverse proxyA server that sits in front of your servers and speaks for them. The client only ever knows the proxy.
    UpstreamNginx's word for a backend server, or for a named group of them. upstream api_backend { … }.
    Round robinSend request 1 to server A, 2 to B, 3 to C, 4 to A… Nginx's default, and correct when all backends are equal and stateless.
    Sticky sessionPinning a client to one backend so its in-memory state is there. A workaround for stateful backends; we need none.
    Passive health checkJudging a backend by how real traffic to it behaves. All open-source Nginx has. The opposite is an active check that probes on a timer.
    KeepaliveReusing one TCP connection for many HTTP requests instead of reconnecting each time. Applies both browser↔Nginx and Nginx↔backend.
    MicrocacheCaching for a very short time — one or two seconds — so a burst of identical requests collapses into one backend call.
    Thundering herdEvery client becoming a cache miss at the same instant when an entry expires, stampeding the backend.
    Leaky bucketRate-limit model: a bucket drains at a fixed rate, each request adds a drop, overflow is rejected. burst is the depth, nodelay whether queued drops wait.
    TLS terminationDecrypting HTTPS at the proxy and talking plaintext to the backends.
    ALPNThe TLS extension that negotiates the protocol during the handshake — how a client and server agree on h2 rather than http/1.1.
    HSTSA header telling the browser “never use plain HTTP for this host again”. The browser remembers, which is why it is risky on localhost.
    CSPContent Security Policy — a header telling the browser which sources of script, style and connection are allowed. The main defence against XSS execution.
    SPA fallbackServing index.html for any URL that is not a real file, so a client-side router can handle it. Without it, refreshing a deep link 404s.
    Row lockAn exclusive lock on one table row. A second writer to that row blocks until the first commits or rolls back.
    MVCCMulti-Version Concurrency Control — writers create new row versions instead of overwriting, so readers never block writers.
    READ COMMITTEDPostgres' default isolation level: each statement sees a fresh snapshot of committed data. The per-statement part is what makes the idempotency replay work.
    EvalPlanQual recheckWhen an UPDATE unblocks after waiting on another transaction, Postgres re-reads the new row version and re-evaluates the WHERE clause against it. The mechanism that makes a conditional UPDATE race-free.
    Lost updateTwo transactions read, both decide, both write — and one decision silently vanishes. What a read-then-write gap causes.
    IdempotencyDoing something twice has the same effect as doing it once. GET and DELETE are naturally idempotent; POST is not, which is why it needs a key.
    Optimistic vs pessimistic lockingOptimistic: assume no conflict, detect it at write time, retry. Pessimistic: take the lock up front and make others wait. Flash sales want pessimistic.
    SAVEPOINTA nested rollback point inside a transaction. Lets one failed statement be undone without poisoning the whole transaction.
    Lazy expiryTreating something as expired when you read it, rather than running a job to clean it up.
    Connection poolA reusable set of database connections. Postgres backends are processes, so opening one per request would be very expensive.
    SlowlorisAn attack that opens many connections and sends them byte by byte, exhausting connection slots using almost no bandwidth.
    Thundering 429 vs 503429 = “slow down, retry after N”. 503 = “the server is broken”. Clients treat them very differently.
    envsubstA shell tool that substitutes environment variables into a template. With no argument it replaces every $name — including the ones your config needs.
